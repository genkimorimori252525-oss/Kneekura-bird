# Isolated benchmark stop probe

This is a test-only fixture for a specific safety question: does the public `BenchmarkManager.stop(CommandSourceStack)` remove a real benchmark aircraft while a player controls it? No real MOD run of this fixture has been performed as part of its implementation. Source inspection of the current `stop` → `abort` → `cleanup` path suggests that it can discard the aircraft; that is a hypothesis, not a runtime result. This probe does not change production flight, player, or benchmark behavior.

## Isolation is required before any execution

The second case deliberately invokes a potentially destructive stop. Run it only in a new, disposable world in a dedicated JVM, with no live players, other benchmark sessions, concurrent GameTests, or other chunk-force owners. The fixture's system property is an operator attestation, **not proof** of world freshness, isolation, chunk ownership, or version. It checks `GameTestServer`, its dedicated namespace, and exactly one registered test with the expected name, batch, and template. It refuses a public stop unless the currently registered session is the exact instance it created. This identity check and the call are not atomic; isolation is essential. A zero-test run never enters the guard and can still exit successfully: an external review must confirm exactly one test and its explicit markers.

`prepareFlightGameTestRuntime` uses the fixed `ww-debug-benchmark/run-gametest` path and deletes that directory's staged `mods` and profile. Before any future run, inspect the task and all configured paths; establish that this path and its parent have the expected canonical locations with no symlink redirection and that the run directory does not already exist. Verify no other JVM uses the world. Create a separate empty evidence directory outside the worktree, capture input hashes and the exact source/init-script revision, stdout, stderr and exit code, and retain the complete world even on failure or timeout. Never use an existing user world or infer safety from the property or a successful exit alone. Do not enable Actions or change runner settings.

The supplied original MOD inputs previously used with #141 were Minecraft 1.20.1, Forge 47.4.20, Immersive Aircraft 1.3.3 SHA-256 `d1f7cfeed3ac2cf69472ae756eb9189dad04ab21b8afbd443c82f40e51bbf065` and Warfare Wings 1.1.4 SHA-256 `3b6b245e703862517fe7aae6acd95ccafc865e1e81ba7a26e2b9abcfe1120187`; Java 17.0.17 and Gradle 8.8 were used. Independently check staged inputs and applicable reuse conditions. The fixture does not distribute these MODs. The dedicated init script is `ww-debug-benchmark/tools/benchmark-stop-isolated.init.gradle`; it sets the namespace and attestation for `runGameTestServer` and checks the configured working directory and JVM argument providers. It does not create or verify a fresh world.

## Interpretation

The only expected test is `benchmarkstoprespectsplayer`, batch `benchmark_player_stop_probe_only`, structure `wwdebug_benchmark_stop_probe:empty`. The recorded 25-chunk initial set must equal the GameTest structure's fixed footprint. First, a player-free D4Y session with its ArmorStand controlling is used to check that a deliberately different session identity is refused without removing the session, aircraft, pilot or control entry (`foreign_identity_refused`). It is then stopped through the public method; a `positive_pass` marker requires result 1, removal of both identified entities, empty benchmark maps and restored forced-chunk set. Only then is a distinct D4Y session created. While the second aircraft is still player-free, the test sets and reads back finite nonzero engine, control, position and velocity sentinels. A `FakePlayer` mounts through normal `startRiding`; the test checks that mounting preserved the sentinels and verifies that it controls the aircraft with the original ArmorStand aboard and records UUIDs and control/motion values. The same public stop is called, and the test records whether the original aircraft and player survived, the rider remains attached and controlling, and the recorded values remain the same. `player_pass` appears only after these checks and verification that the session and its control/heartbeat entries are gone. Exact snapshots do not detect same-value writes.

A valid result requires the selected-test record, `foreign_identity_refused`, `positive_pass`, player-before and player-after records, cleanup record, the GameTest result and process exit status, reviewed together. A concrete logged aircraft removal or rider detachment is a safety violation; a missing marker, failed setup, missing UUID lookup, exception, ambiguous selection, or cleanup error is inconclusive and is not evidence of a fix. In particular, `stop` removes the session from its map before `abort`, so an exception may leave partial effects. Preserve the world and logs. The fixture dismounts only its FakePlayer and attempts best-effort cleanup only of its known registered session after checking that no different session is present and no player remains aboard. It does not guess unknown objects or blanket-unforce chunks. A constructor failure can leave effects before an owner is returned; manual analysis of the preserved disposable world is then required.

The 25-chunk comparison observes set membership, not ticket ownership or intermediate changes. Existing benchmark cleanup uses shared boolean forced chunks, so equality cannot establish that overlapping owners are safe. The attested absence of other owners, a fresh isolated world, and retained evidence are required even if the comparison succeeds. The test covers one artificial `FakePlayer`, a single D4Y and direct public method invocation; it does not prove behavior for a networked player, other aircraft, overlapping ownership, command parsing, concurrent/reentrant activity, attitude, or same-value writes. It does not exercise natural long-running flight or the separate phase-reset path.
