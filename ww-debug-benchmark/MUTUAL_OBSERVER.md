# Local reciprocal-dogfight observation

This diagnostic is for the A6M `dogfight_mutual` GameTest. It is disabled unless the server is a `GameTestServer`, the configured and actual primary entity registry IDs are both `warfare_wings:a6m`, and the exact system property `wwdebug.mutualObserveEntity=true` is supplied for that scenario. If the registry ID cannot be read, the observer stops without logging. Gradle's GameTest run forwards `-PmutualObserveEntity=true`; ordinary server runs and runs without that exact opt-in do not emit observation events. The observer never asks for or forces a chunk and does not change control inputs, safety thresholds, physics, or entity scheduling. Extra event writing can still add runtime overhead, so results must be kept separate from runs without the probe.

`mutual_dogfight_entity_observation` events are written to the primary aircraft's usual buffered telemetry. The initial `after_fixture_direct_apply_before_opening` event follows the fixture's explicit opponent `applyControl` and mission seed, but precedes the opening adapter's move: it is not proof of an opponent entity tick. Later `before_rebind` samples occur at overworld game-time multiples of 20, while the primary scene callback is executing, before its missing-opponent/reload branch. If the primary callback does not run, this probe cannot sample. Short gaps may fall between samples.

The event records the primary position and `tickCount`; the scene's opponent UUID; whether the UUID lookup is visible and whether it resolves to the same retained scene reference; and the reference's UUID, position, chunk, `tickCount`, removed/added flags and controlling passenger. `uuid_session_mission_ticks` looks up a session by the reference UUID; it does not prove that session owns that particular reference if different objects share a UUID. The reference may be stale: its position and chunk are last-known object fields, not necessarily a currently ticking entity. `unknown` is distinct from `false` and `none`; a lookup returning `not_visible` does not prove the entity is absent from the world. If a query fails, the probe attempts an `observation_error` event and the sample is unverified. A missing probe event, buffered write, or no logged error does not prove that any logger call succeeded or data reached durable storage.

`chunk_has_holder` is `ServerChunkCache.hasChunk` for the retained reference's chunk, not a guarantee that the entity ticked or even that a `LevelChunk` is available. `chunk_entities_loaded` checks the entity section load state; `position_entity_ticking` checks the position's entity visibility and ticking-ticket range. The latter values are `unknown` when the reference is not in the primary's level. These are point-in-time queries, not the actual scheduler decision. In this Minecraft version, a non-passenger entity's `tickCount` increases before `canUpdate` is tested, so an increment does not prove that `Entity.tick()` or autopilot logging ran. Logger success, intermediate movement, other chunk tickets and causality remain unobserved.

The accompanying opt-in fixed-UUID fixture is experimental and **does not establish that a reused world is safe**: an existing UUID in an unloaded section may evade visible-entity lookup. Before any future run, use a separate JVM and prove that the selected actual world is fresh, including the working directory, `server.properties` level name, resolved paths and symlinks. Preserve previous worlds and logs. Record the commit, JAR and profile hashes, seed, JVM properties, UUID plan, world path, complete event logs and observer limitations; do not treat a missing/error observation as a successful measurement. This document does not authorize an additional GameTest run.
