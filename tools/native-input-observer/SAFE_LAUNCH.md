# Experimental observer launcher

This is a test-only entry point for a fresh, isolated GameTest experiment. It does not establish that an observer is discovered, its mixin is applied, a setter hook ran, or a GameTest passed. The source at base commit `10923117a121382c93f2f888554e178c0478a96a` does not wire this observer into the natural-tick fixture; no real MOD execution has validated this launcher. The ordinary project build, MOD manifest and ordinary Gradle entry points are unchanged.

Before a future invocation, independently establish all of the following: an isolated disposable environment with no other JVM, tests, player or chunk owner; externally enforced network isolation; an independently created private and exclusively used Gradle user home containing the necessary trusted offline dependency cache and no credentials, init scripts or Gradle properties; trusted Python, Git, Java 17 and Gradle 8.8 distributions and cache; a new scratch path under a private parent; and verified hashes of the original fixed MODs and the exact standalone observer jar. The known shared Cloud home `/workspace/.cloud-setup/gradle-home`, its ancestors and descendants are rejected. The dedicated home must be owned by the current user with no group/other permissions; its tree is checked for symlinks, hardlinks and special files. Prepare a real copy, not hardlinks, and ensure nothing else uses it. Gradle writes to the supplied dedicated home as well as scratch. The launcher does not create or verify a dedicated cache, verify the full JDK/Gradle distributions, identify another process, or enforce network isolation. Executable hashes cover individual files only. The three required `--*-attested` flags record these assertions; they do not prove any of them.

Invoke the fixed CLI using `python3 -I tools/native-input-observer/safe_launch.py` with the explicit required arguments shown by `--help`. Scratch, jar, Java home, Gradle executable and dedicated Gradle home paths must be absolute. The MOD hashes are built into the launcher; the caller supplies and pins an observer SHA-256, Java executable SHA-256, and Gradle script SHA-256 for the attempt. No arbitrary Gradle options are accepted. The child receives an explicit environment, no user `JAVA_TOOL_OPTIONS`, `GRADLE_OPTS`, profile override or extra init scripts. User-home init/properties and installation init scripts/properties are rejected. The observer remains a separate experimental jar, and no MOD contents are redistributed here.

The launcher makes a new mode-0700 scratch and exclusive attempt lock, then extracts only regular `ww-debug-benchmark` files from the fixed local git commit. The tracked `run-gametest/server.properties` is deliberately *not* extracted so the entire run directory is absent before preparation. It does not delete or modify the original checkout or an existing run directory. Consequently, settings can differ from prior runs that had a server.properties file; effective runtime settings must be separately recorded and compared before treating scenarios as equivalent. The copied MOD and observer bytes are hashed again, and the sole Gradle task, environment and init script are fixed. No external JVM is signalled or terminated.

The dedicated init script checks input hashes and requires a nonexistent run directory in `prepareFlightGameTestRuntime.doFirst`. The fixed project has a build-resource dependency that can write within this new scratch before this guard. Only after the whole prepare task reports executed, successful and not skipped does `afterTask` authorize the subsequent `runGameTestServer.doFirst` to create a new `mods` directory and copy exactly one observer jar without replacement. The staged jar is rehashed before JVM launch. A failed or interrupted copy may leave a partial jar in the disposable scratch; it is not a successful staging record. Marker lines are checked for exact identity, uniqueness and order in the preserved stdout. Post-run stdout parsing is limited to 128 MiB; this is not a runtime output-size or storage quota, so impose one externally.

`scratch/provenance.json`, stdout/stderr, exit code, launcher status and the entire world remain in place. An error after scratch creation is recorded when possible; failures before creation have terminal diagnostics only. The launcher never deletes a scratch, lock, world, log or existing file. A Gradle exit code of zero and `launcher_completed_runtime_unverified` mean only that the process exited zero with the three launcher ordering markers. They are **not** proof of isolation, fixture selection, observer discovery, hook coverage or an accepted result. Zero GameTests can exit zero. The separately specified test markers, observer closed report and runtime provenance must be independently checked; any missing, ambiguous or failed evidence is inconclusive. Never post local paths, credentials or private information into public evidence.

The lock coordinates this attempt and a second launch cannot reuse its scratch. It cannot prevent another same-UID process from modifying a directory after inspection or an unrelated JVM from acting elsewhere. Canonical-path/symlink and hash checks do not exclude bind mounts, hard-to-observe concurrent processes, path swaps between checks, stale caches or malicious dependencies; no portable isolation guarantee is claimed. Use a separate disposable user/container/volume and enforce process and network isolation externally. The byte-copy-to-final-name is exclusive, not atomic against process death or an adversarial same-UID writer. The `afterTask` ordering and refusal paths have only been exercised with a miniature local Gradle graph and fake bytes, not this project's real tasks or MOD. If any assumption cannot be established, do not run the experiment; preserve the attempt and report it as unverified. To revert, stop using the launcher; removal of disposable scratch is a later manual evidence-retention decision.
